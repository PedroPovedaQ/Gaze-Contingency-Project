\chapter{EXPERIMENTAL PLATFORM FOR THE VOICE COMPARISON}
\label{ch:system}
The platform delivers the self-similar and preferred catalog voices within the same search task. Its role is to preserve a common assistance policy while recording the speech and interaction that each participant experiences. Voice preparation and delivery define the manipulation; gaze sensing, local state, and constrained agent decisions determine when the shared guidance is appropriate. Figure~\ref{fig:architecture} summarizes that supporting pipeline, while Appendix~\ref{app:guidance-support} retains detailed state transitions, memory settings, and cancellation behavior.

\section{Voice Preparation and Telemetry}
All voice audio is pre-synthesized with ElevenLabs, which supplies both the catalog voice and the self-similar voice. To support the self-similar condition, each participant records the same standard passage in their usual speaking voice. Both conditions share the semantic phrase library, guidance policy, and playback routing, so voice condition is the intended manipulation; behavior-dependent wording, hint counts, and synthesized acoustics nevertheless need not be identical. The preparation pipeline checks wording and library readiness, but per-voice intelligibility, loudness, and acoustic comparability still require pilot verification, because automated checks do not establish perceptual equivalence. No pitch or spatial effects are applied to the self-similar voice. We log the provider, model, voice ID, library version, and synthesis settings.

The Trial Review application aligns gaze and controller state, guidance transitions, agent decisions, and playback events with trial geometry on a common timeline. Trial-level aggregates are stored separately from the raw gaze, motion, and event streams. The effective gaze sampling rate must be verified from distinct source timestamps on the tested headset build rather than inferred from the nominal specification or the application polling rate. Similarly, the analysis will report ray intersections as gaze hits and will not label them as fixations unless a validated event classifier is applied.

\section{Apparatus}
The application is developed in Unity 6 (6000.3.10f1) using the Unity OpenXR Plugin (1.16.1), HTC VIVE OpenXR integration (2.5.1), and Unity XR Interaction Toolkit (3.3.1). It is deployed as a standalone Android ARM64 application on the HTC VIVE Focus Vision head-mounted display, with rendering performed locally on the headset using the Universal Render Pipeline (17.3.0). The headset supplies head-pose and eye-gaze tracking, while the tracked right-hand controller supplies pointing and trigger input. Video passthrough supports the mixed-reality view. Network access supports cloud-based agent decisions and voice preparation; it is not used to stream rendered frames from a host computer.

\section{Search Task}
The search task takes place in mixed reality, with video passthrough showing a neutral physical room. Participants will sit on a swivel chair and interact using the right controller, while virtual colored geometric objects hang on eight vertical planes anchored along the surrounding walls; Figure~\ref{fig:scene} shows the layout from above. Because the application holds the target identity and withholds it from the opening instructions, participants must rely on voice guidance to locate the target, which they select by pointing the controller ray at it and pressing the trigger. Stimulus density and spatial bounds will be frozen for the study release after seated-comfort and ray-selection pilots. For each trial, the system logs object positions, layout seed, wall assignment, and target identity.

\section{Sensing and Guidance State}
The system continuously collects eye-gaze origin, direction, and validity; head pose; right-controller pose; and ray-object intersections. A local state machine combines these observations with the target geometry to track the participant's progress through the search: turning toward the target wall, refining within the wall, acquiring the target with gaze, pointing with the controller, and becoming ready to select. Additional states cover suspended or paused operation. Each state transition is logged with its cause.

Because guidance is only as reliable as the evidence behind it, the state machine issues new gaze-dependent guidance only when gaze data are valid and recent. Gaze ray hits, gaze-vicinity candidates, and controller hits are treated as separate observations; when gaze-vicinity regions overlap, the closest object is chosen as the vicinity candidate. A controller ray hit on the target immediately suppresses contradictory directional cues, whereas the spoken pointing acknowledgment separately requires a one-second controller hold with valid nearby gaze when speech is admitted. This suppression is intended to prevent away-directions during the qualification interval without falsely acknowledging an unqualified hold. Gaze confirmation, controller confirmation, and trigger selection are recorded as distinct events.

\section{Agent Decisions and Playback Control}
Jev selects from a constrained set of options rather than generating free-form instructions. Local geometry and state rules first filter the phrase library to candidates that are valid in the current situation, and each request to Jev then contains a state snapshot, recent memory, playback status, and two to five eligible phrases. From these, Jev chooses the wording and whether to speak now or wait, while target definition and geometric reasoning remain local. Eligibility filtering and playback revalidation are intended to reduce spatially incorrect or stale guidance. Tracking error, imperfect geometry, and software faults can nonetheless produce unhelpful instructions, so recorded-sequence and headset checks remain necessary.

Because cloud responses arrive asynchronously, the participant's state may change before a decision returns. A local speech scheduler therefore revalidates each decision against the current state, evidence, pacing, and object intersections before playback, and discards decisions that are stale or conflict with the current situation. Qualified gaze and controller acknowledgments and eligible turn-progress milestones can use local handling and are played from prepared phrases without waiting for a new cloud decision, subject to the same checks. Each completed or interrupted utterance updates both the memory and the event log. Model latency, deferral, cancellation, fallback, and playback onset are logged separately to support delay attribution. When a trace lacks the required events, the cause remains unknown rather than inferred from the spoken phrase alone.

\section{Delivery Quality as an Experimental Requirement}
Both voices must receive the same versioned guidance mechanism, but their delivered sequences will still depend on participant behavior and their clips may differ acoustically. The relevant control is a shared policy with documented exposure, not an assertion that every participant hears an identical sequence. Voice identity, library metadata, playback onset, and delivery faults must remain traceable to the corresponding condition.

A delayed or confusing cue matters here because it could alter search performance or a participant's judgment of the voice. Technical inspection therefore supports interpretation of the voice contrast. Appendix~\ref{app:guidance-support} explains how the implementation can be checked, and Appendix~\ref{app:decision-contract} preserves the inspected provider contract. Neither substitutes for the participant evidence needed to evaluate self-similar voice.
