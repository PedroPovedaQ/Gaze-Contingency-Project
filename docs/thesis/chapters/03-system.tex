\chapter{METHODOLOGY}
\label{ch:system}
This chapter describes the application, experimental design, procedure, and data collection used to examine self-similar spoken assistance in virtual reality. The study compares performance, perceived workload, motivation, and agent experience across self-similar and neutral voices within the same gaze-contingent search task. Voice condition is the experimental factor; gaze sensing, spoken spatial guidance, and right-controller selection remain common to both conditions.

The application runs on the HTC VIVE Focus Vision headset. Each participant completes one practice trial and 80 measured trials, divided into two counterbalanced blocks of 40 trials, one per voice condition. The project source is available at \href{https://github.com/PedroPovedaQ/Gaze-Contingency-Project}{the Gaze Contingency Project GitHub repository}.

The methodological choices are informed by Chiossi et al.'s visual-search study, which combines search outcomes with eye-tracking measures~\cite{chiossi2024searching}. The present study adopts that separation between task performance and visual behavior while changing the research question to voice identity, withholding the target identity initially, and using a researcher-selected 25-second search limit. Complementary work by Pfeil et al. at UCF compares eye--head coordination in virtual and physical viewing~\cite{pfeil2018eyehead}; it motivates retaining head motion alongside eye direction when interpreting gaze in this application.

\section{Application Design}
The application presents a virtual setup menu before the search task. Participants choose a neutral voice from the supplied options, record a standard passage for their self-similar voice, and confirm that both voices are clear and comfortable to hear. Voice preparation and eye-tracking setup precede practice. During search, participants remain seated on a swivel chair, inspect the surrounding scene, and use only the right controller for pointing and selection.

\subsection{Apparatus}
The application is developed in Unity 6 (6000.3.10f1) using the Unity OpenXR Plugin (1.16.1), HTC VIVE OpenXR integration (2.5.1), and Unity XR Interaction Toolkit (3.3.1). It is deployed as a standalone Android ARM64 application on the HTC VIVE Focus Vision head-mounted display, with rendering performed locally on the headset using the Universal Render Pipeline (17.3.0). The study uses the headset's virtual-reality configuration, in which the headset supplies head-pose and eye-gaze tracking and the tracked right-hand controller supplies pointing and trigger input. Network access supports cloud-based agent decisions and voice preparation; it is not used to stream rendered frames from a host computer. HTC specifies 2448 $\times$ 2448 pixels per eye, a 90-Hz standalone display refresh rate, and a field of view of up to 120 degrees~\cite{htc2026focusvision}. The advertised 120-Hz binocular gaze output is a sensor specification; the application's effective rendering and gaze-delivery rates will be measured on the study build.

\subsection{Objects, Planes, and Selection}
The search task takes place in a neutral virtual room. Seated participants interact using the right controller, while colored geometric objects hang on eight vertical planes arranged around them; Figure~\ref{fig:scene} shows the layout from above. Because the application knows the target identity but withholds it from the opening instructions, participants must rely on voice guidance to locate the target, which they select by pointing the controller ray at it and pressing the trigger. The stimulus generator includes six shapes---sphere, cube, pyramid, cylinder, capsule, and star---in red, blue, yellow, and green. Eight vertical planes surround the seated origin at 45-degree intervals. The development configuration contains 168 objects, or 21 per plane, at a default plane radius of 1.5~m from the seated origin; these object counts are unrelated to the eight trials assigned to each absolute nominal angle in a 40-trial block. Objects vary in height and horizontal position within their assigned plane, so search requires both coarse orientation toward a plane and finer search within it. For each trial, the system logs object positions, layout seed, wall assignment, and target identity.

Each wall is 2.2036~m high (approximately 2.20~m), 30\% lower than the 3.148-m walls of earlier development layouts. Object centers occupy heights from 0.10~m to 2.1036~m above the floor, leaving a 0.10-m margin above the highest permitted center, and are separated by a minimum three-dimensional center-to-center distance of 0.20~m. Layouts are generated from a saved seed; for measured trials, final positions also depend on the eye origin saved at readiness completion.

Both voice conditions use the same layout and spatial constraints. Pilot sessions will assess seated comfort, visibility, ray selection, and realized height allocation before these parameters are fixed for participant collection.

\subsection{Voice Preparation and Audio}
All voice audio is pre-synthesized with ElevenLabs, which supplies both the neutral voice and the self-similar voice. To support the self-similar condition, each participant records the same standard passage in their usual speaking voice. Both conditions share the semantic phrase library, guidance policy, and playback routing, so voice is the intended manipulation. Because guidance responds to behavior, however, the wording and number of hints can differ between blocks, and the synthesized clips can differ acoustically. The preparation pipeline automatically checks wording and library readiness, but these checks do not assess perceptual equivalence; pilot sessions will therefore verify per-voice intelligibility, loudness, and acoustic comparability. No pitch or spatial effects are applied to the self-similar voice. The system logs the provider, model, voice ID, library version, and synthesis settings.

The Trial Review application aligns gaze and controller state, guidance transitions, agent decisions, and playback events with trial geometry on a common timeline. Trial-level aggregates are stored separately from the raw gaze, motion, and event streams. The effective gaze sampling rate will be determined from distinct source timestamps on the study headset build rather than from the nominal specification or the application polling rate. The analysis will report ray intersections as gaze hits, which approximate, but are not equivalent to, fixations identified by a validated event classifier.

\subsection{Sensing and Guidance State}
The system updates spoken directions from evidence of the participant's progress, so that instructions can shift from orientation toward a wall to refinement around an object. The same sensing and state logic serves both voice conditions.

The system continuously collects eye-gaze origin, direction, and validity; head pose; right-controller pose; and ray-object intersections. A local state machine combines these observations with the target geometry to track the participant's progress through the search: turning toward the target wall, refining within the wall, acquiring the target with gaze, pointing with the controller, and becoming ready to select. Additional states cover suspended or paused operation. Each state transition is logged with its cause.

The state machine issues new gaze-dependent guidance only when gaze data are valid and recent. Gaze ray hits, gaze-vicinity candidates, and controller hits are treated as separate observations; when gaze-vicinity regions overlap, the closest object is chosen as the vicinity candidate. A controller ray hit on the target immediately suppresses contradictory directional cues, whereas the spoken pointing acknowledgment separately requires a one-second controller hold with valid nearby gaze when the speech scheduler permits the acknowledgment to play. Gaze confirmation, controller confirmation, and trigger selection are recorded as distinct events.

\subsection{Agent Decisions and Playback Control}
Jev, the cloud decision agent shared by both voice conditions, selects from a constrained set of options rather than generating free-form instructions. Local geometry and state rules first filter the phrase library to candidates that are valid in the current situation, and each request to Jev then contains a state snapshot, recent memory, playback status, and two to five eligible phrases. From these, Jev chooses the wording and whether to speak now or wait, while target definition and geometric reasoning remain local. Eligibility filtering and playback revalidation are intended to reduce spatially incorrect or stale guidance.

Because cloud responses arrive asynchronously, the participant's state may change before a decision returns. A local speech scheduler therefore revalidates each decision against the current state, evidence, pacing, and object intersections before playback, and discards decisions that are stale or conflict with the current situation. Qualified gaze and controller acknowledgments, together with eligible turn-progress milestones, can be handled locally and played from prepared phrases without waiting for a new cloud decision; they remain subject to the same checks. When a qualified target acknowledgment would replace misleading search speech, a local fast path avoids waiting for interruption advice. This path protects the first 0.35 seconds and final 0.5 seconds of the current phrase, retains a 2.5-second interruption cooldown, and fades the audio over 150 ms. The fast path keeps the separate gaze and controller hold requirements, and fresh evidence is checked before the fade, after it, and at playback. Setup, completion feedback, and existing acknowledgments are protected from interruption. Each completed or interrupted utterance updates both the memory and the event log. Model latency, deferral, cancellation, fallback, and playback onset are logged separately to support delay attribution. When a trace lacks the required events, the source of a delay is recorded as unknown rather than inferred from the spoken phrase alone.

\subsection{Delivery Quality as an Experimental Requirement}
Both voice conditions use the same versioned guidance mechanism, although delivered sequences depend on participant behavior and clips may differ acoustically. Voice identity, library metadata, playback onset, and delivery faults are therefore recorded so that each can be traced to its condition.

A delayed or confusing cue could alter search performance or a participant's judgment of the voice, and could then be mistaken for an effect of voice condition. Appendix~\ref{app:scenarios} defines guidance sequence tests and an evaluation rubric for checking the implementation.
