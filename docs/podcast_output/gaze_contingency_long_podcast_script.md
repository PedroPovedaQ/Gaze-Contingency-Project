**Maya:** The project begins in Unity with a scene called `GazeContingencyStudyScene.unity`. That is important because a mixed reality experiment is not only a visual interface. The PDF identifies `FindObjectGameManager.cs` as the owner of the experiment state machine. **Leo:** And then `FindObjectUI.cs` owns the visible study HUD. In a user study, the HUD matters because it tells the participant what to do without letting the interface become the task. **Maya:** That first section of the flowchart is basically a launch fan-out. The app launches. One branch detects the table plane. Another shows the start prompt. Another prepares voice and game systems. This is a good design pattern in mixed reality because the system needs several conditions to be ready before the participant can begin. **Leo:** The next step is plane detection. The PDF names `VivePlaneProvider.cs` as the component that detects the usable table plane in mixed reality. That means the headset and application need to understand a real-world surface where virtual objects can be placed. For an object search task, this is foundational. If the bookshelf or object layout floats in the wrong place, clips through the table, or appears at an unstable angle, then the participant is no longer just performing a visual search task. They are also fighting spatial registration problems.

**Maya:** Once the plane is detected, the participant sees a start prompt from `FindObjectUI.cs` and taps the table to begin. That tap is not just a button press. It is an experimental boundary. Before the tap, the participant is in setup. After the tap, the system can begin the controlled sequence that produces analyzable data. `FindObjectGameManager.cs` receives that tap and checks whether the spoken introduction is still playing. That is a subtle but important detail. The system does not automatically start the trial just because the participant tapped.

**Leo:** Exactly. The PDF calls this the intro gate. If the spoken introduction is still running, the visible prompt changes to "Please wait..." and the game waits until `VoiceAssistantController.cs` finishes the intro. Only once that gate clears does `FindObjectGameManager.cs` start the session for real. This matters because audio instructions and task timing can otherwise overlap. If the first round starts while the participant is still hearing the rules, their early gaze behavior could reflect confusion or divided attention rather than search strategy.

**Maya:** The intro gate also shows a general principle in experimental software: do not let user impatience accidentally corrupt the timing model. Participants often tap quickly. They may not realize the system is still in an instruction phase. A robust state machine absorbs that tap, gives a clear "Please wait..." response, and starts only when the conditions are right. That makes the data cleaner and the participant experience less ambiguous.

**Leo:** After the intro gate clears, we reach the actual experiment start. From there, the system goes into round presentation and object spawning. At the beginning of each round, `FindObjectUI.cs` shows the fixation cross and task UI, while `VoiceAssistantController.cs` announces the current goal. The fixation cross is a classic study tool. It helps normalize where the participant is looking before search begins. In a gaze study, that matters because initial gaze position can affect the first fixation, search path, and any interpretation of how quickly someone found the relevant region.

**Maya:** Then the environment gets populated. `ShelfSpawner.cs` creates the bookshelf layout and spawn positions. The name suggests it is responsible for arranging the spatial structure where objects will appear. This matters because object search is strongly shaped by layout. The participant is not just searching a list. They are searching a spatial scene. The density of objects, the shelf geometry, the relative positions, and the visibility of targets can all influence performance.

**Leo:** After spawning, `ShapeObjectFactory.cs` post-processes spawned prefabs into the actual experimental stimuli. I like that separation. One component can decide where objects go, and another can decide what those objects become. That helps keep layout generation separate from stimulus identity. It also makes the experimental logic easier to reason about. If a target should be a particular shape or color, that transformation belongs in the stimulus generation layer rather than being mixed into table detection or UI code.

**Maya:** Then `SpawnableObjectInfo.cs` attaches metadata used by gaze logic, capture logic, and analysis. This is one of the most important behind-the-scenes pieces. The participant sees objects. The system needs to know what each object means. Is it the current target? What is its identity? Where was it spawned? What label should appear in the logs? What object did the participant dwell on? If that metadata is not attached cleanly, the gaze logger might know that the user looked at a collider, but the analysis pipeline might not know what that collider represented.

**Leo:** This is where the project moves from a mixed reality app into a research instrument. A demo can get away with visual effects. A study needs traceable meaning. Every spawned object needs enough identity to connect the user's behavior to a trial condition, a target, and an outcome. `SpawnableObjectInfo.cs` acts like a bridge between Unity objects in the scene and rows of data that will later be analyzed.

**Maya:** Now we get to the central mechanism: gaze interaction and dwell capture. During search, `GazeHighlightManager.cs` tracks the currently hovered object and applies dwell-based capture. The PDF describes it as the main bridge between raw gaze interaction and the study task. That phrase is worth pausing on. Raw gaze is continuous. It is noisy. It changes every frame. But the study needs discrete events, like "the participant selected object A at this time." Dwell capture converts sustained attention into an intentional or semi-intentional selection.

**Leo:** Dwell selection is especially interesting in mixed reality because it avoids requiring a controller click or hand gesture for every selection. The participant looks at an object, and if the gaze remains there long enough, the system treats that as capture. But dwell introduces design questions. How long is long enough? Too short, and accidental glances become selections. Too long, and the task feels sluggish. The PDF does not specify the dwell threshold, but the architecture clearly makes `GazeHighlightManager.cs` responsible for that conversion from hovered object to captured object.

**Maya:** There is also a conceptual distinction between looking and selecting. In normal search behavior, people look at many wrong objects before finding the right one. If the system treated every fixation as a committed answer, the task would be frustrating and the data would be noisy. Dwell is a compromise. It says, "A brief glance is inspection. Sustained gaze is selection." That lets the system preserve natural visual search while still creating a measurable endpoint for each attempt.

**Leo:** Once dwell capture completes, the selection goes back to `FindObjectGameManager.cs`, which decides whether the selected object matches the current target. This is another reason why the game manager is the state machine owner. It knows the current goal. It can compare selected metadata against the target metadata. If the object is correct, the experiment advances to the next round or finishes the study. If the object is wrong, the system triggers feedback.

**Maya:** That feedback runs through both `FindObjectUI.cs` and `VoiceAssistantController.cs`. So a wrong selection can produce visible feedback and audio feedback. The flowchart says "Show wrong feedback plus play buzz." That tells us the design is multimodal. The participant gets immediate confirmation that the selected object was not right. That is useful for task flow, but it is also relevant to data interpretation. Wrong selections are events. They are not invisible failures. They become part of the participant's path through the round.

**Leo:** Correct selections are also state transitions. A correct selection can move to the next round or finish the study. That means the system probably has a list of target trials, a current round index, and some end condition. The PDF does not go into those implementation details, but the state machine role makes sense. The game manager is the traffic controller. It coordinates UI, voice, object setup, gaze selection, and logging as the participant moves through the study.

**Maya:** The most distinctive feature is hint generation. `HintGenerator.cs` runs alongside the interaction loop. In gaze-aware rounds, it converts current gaze behavior into temperature-style feedback such as cold, on track, or very close. In gaze-unaware rounds, it gives generic encouragement without using gaze state to personalize the content. This is the experimental contrast. The project can compare assistance that reacts to gaze against assistance that does not.

**Leo:** Temperature-style feedback is a smart metaphor because it is easy to understand without overexplaining. "Cold" means you are far from the target. "On track" means your current search behavior is aligned with the target region or object class. "Very close" means you are near the right object. The interesting part is how gaze behavior gets mapped to those categories. The system can watch which object or region is currently being inspected and generate feedback based on proximity to the target or relevance to the goal.

**Maya:** And the gaze-unaware condition matters because it creates a baseline. If every participant gets some encouragement, then the study can ask whether gaze-contingent assistance adds value beyond general prompting. Without that baseline, any improvement might simply come from having an assistant voice in the task. With gaze-aware and gaze-unaware rounds, the project can make a cleaner comparison.

**Leo:** There is also a user-experience balance here. Gaze-aware hints can be helpful, but they can also become intrusive if they fire too often or feel too obvious. The assistant should not constantly narrate every eye movement. It should help at moments where assistance is useful. The PDF does not describe the timing policy, but architecturally, `HintGenerator.cs` sitting alongside the interaction loop suggests a continuous or repeated evaluation of gaze state, with some logic deciding when and what to say.

**Maya:** That raises a deeper point about gaze-contingent AI assistance. Gaze is a powerful signal, but it is not mind reading. If someone looks at the wrong object, they might be confused, comparing options, checking distractors, or simply passing through the scene. The system has to be careful about how strongly it interprets gaze. Temperature-style hints are useful because they avoid overclaiming. Instead of saying "you are thinking about the wrong object," the system says something like "cold" or "very close," which guides without pretending to know intent perfectly.

**Leo:** The architecture also separates gaze capture from hint generation. `GazeHighlightManager.cs` handles what is being hovered and when dwell becomes capture. `HintGenerator.cs` handles assistance content. That separation is healthy. Selection logic and coaching logic are related, but they are not the same responsibility. A future version could change the hint strategy without rewriting dwell capture. Or it could change dwell timing without rewriting the language of hints.

**Maya:** Now let us follow the data. The PDF names two logging components: `GazeDataLogger.cs` and `TrialDataLogger.cs`. `GazeDataLogger.cs` writes per-frame gaze data. That probably means it records gaze direction, hit object, hit position, timestamps, and maybe current trial context at a high frequency. Per-frame data is detailed enough to reconstruct search behavior, but it can be large and noisy.

**Leo:** `TrialDataLogger.cs` writes event-level logs and per-run summary metrics. That is a different layer of data. Event-level logs might include trial start, target announced, hint delivered, object captured, wrong selection, correct selection, and trial end. Summary metrics might include completion time, number of wrong selections, number of hints, dwell counts, or other aggregate measures. The PDF says the system produces `gaze_log.csv`, `trial_events.csv`, and `trial_summary.json`.

**Maya:** Those three outputs are a good trio. `gaze_log.csv` is the raw behavioral stream. `trial_events.csv` is the interpreted sequence of important moments. `trial_summary.json` is the condensed report for a run. Together they support both detailed and high-level analysis. If a result looks strange in the summary, the researcher can inspect the event log. If the event log raises questions, the researcher can go down into the per-frame gaze log.

**Leo:** This layered logging is especially important in mixed reality because failures can be subtle. A participant might miss the target because the object was placed awkwardly. A gaze ray might hover over the wrong collider. A hint might fire right before a selection and change behavior. If you only have the final score, you cannot diagnose that. With per-frame and event-level logs, you can reconstruct the timeline.

**Maya:** There is a subtle methodological issue here. If gaze is both the selection mechanism and the hint signal, then the system must avoid circularity in interpretation.
